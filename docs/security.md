# Security model

VulnForge Lab is **intentionally insecure**. This document explains how the lab
keeps that insecurity contained.

## Scope

* Use the lab only on a machine you own or are explicitly authorised to test.
* Use it only for scanner benchmarking, training and research.
* Never expose it to the internet, a corporate LAN or a shared CI runner that is
  reachable from untrusted networks.

## Network isolation

| Control | Implementation |
|---|---|
| Loopback binding | Every published port uses `${BIND_HOST:-127.0.0.1}` |
| Internal application network | `lab_net` (gateway to services only) |
| Database network | `data_net` is `internal: true`; scanners cannot reach it |
| SSRF network | `internal_net` is `internal: true` and hosts the metadata simulator |
| Exposed services | `exposed_net` carries only deliberately open services (Redis etc.) |
| Outbound internet | Disabled by default; `ALLOW_EGRESS=true` is required to enable it |

## Container hardening

* `security_opt: no-new-privileges:true` on every service.
* CPU and memory limits declared with `deploy.resources.limits`.
* `pids` limits on the shared anchor.
* No `--privileged`, no host network, no host bind mounts for application code.
* The Docker socket is never mounted into any container.

## Deliberate weaknesses and their guardrails

| Weakness | Guardrail |
|---|---|
| RCE via command injection, SSTI, deserialization | Commands are harmless (`id`, `echo`, `sleep`); no host mounts; container-scoped |
| SSRF | Reaches only `internal_net` and the fake metadata service; egress is blocked |
| Log4Shell-style JNDI lookup | Only an out-of-band HTTP callback; no class loading, no real LDAP |
| Directory listing / backups / `.git` exposure | Synthetic files only; no real source or credentials |
| Default credentials | Fixed synthetic accounts; documented in the catalog |
| Weak TLS profiles | Self-signed certificates generated inside the gateway image |
| Resource exhaustion | Bounded payload sizes; no unbounded real DoS |

## Data

* All records are generated by seed scripts and are synthetic.
* No real personal data, passwords, tokens, private keys or production
  connection strings exist in the repository.
* Secrets that appear in findings (for example the JWT secret `secret`) are
  intentional placeholders and must never be reused.

## Known limitations

* The `data_net` and `internal_net` networks isolate traffic inside Docker, but
  a compromised Docker host removes that boundary. Run the lab on a dedicated
  VM or a dedicated Docker daemon.
* The `legacy-svc` and `auth-svc` banners and metadata are simulated, not real
  vulnerable software packages.
* The Java tier implements the vulnerability classes with the JDK HTTP server
  instead of Spring Boot, so that the image builds deterministically without a
  Maven download. The vulnerability semantics are equivalent for scanning.
* The `node-api` NoSQL injection is modelled with a MongoDB operator evaluator
  over an in-memory store; this keeps reset deterministic without requiring a
  database round-trip. The `mongodb` container is still part of the data layer
  for future persistence work and port-scan scenarios.

## Reporting a problem

If you find a defect in the *lab harness* (not an intended vulnerability), open
an issue at <https://github.com/cumakurt/vulnforge/issues> or contact
Cuma KURT <cumakurt@gmail.com>.

Please do not report intended lab vulnerabilities as security issues; the full
list is in [vulnerability-catalog.md](vulnerability-catalog.md).
